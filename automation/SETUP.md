# RWA Radar 자동 모니터링 — 처음 켜는 방법

## 먼저 확인할 현재 상태

이 문서는 새로 설치하는 경우의 안내입니다. 현재 소유자 저장소 `https://github.com/dooney37/tokenomy-korea-monitor`는 최초 수집과 Pages 피드 발행을 마쳤고, 공개 피드 `https://dooney37.github.io/tokenomy-korea-monitor/monitor-feed.json`을 웹사이트에 연결했습니다. 소유자는 예약 변수 등록 완료를 보고했으나 첫 예약 성공은 아직 확인하지 않았습니다. **이미 설치했다면 새 저장소를 만들거나 이력을 지우지 말고 `automation/UPDATE.md`의 v2 업데이트 절차만 따르세요.** 웹페이지 수정만으로 외부 수집기가 갱신되지는 않습니다. 현재 편집 환경에서는 GitHub 계정·저장소 권한·예약 설정을 대신 활성화할 수 없습니다.

이 구현은 개인 취재기록을 공유 DB로 이관하지 않습니다. **공개 조사결과는 예약 수집기가 JSON 파일로 발행하고, 개인 행사·스피커·섭외 메모·검수 상태는 기존 브라우저에 보존**합니다. 외부 서비스의 비공개 API나 LLM 서비스에 접근하지 않으며 별도 API 키도 사용하지 않습니다.

## 권장 구성: 새 전용 GitHub 저장소 + Actions + Pages 피드

- 예약 실행: GitHub Actions, 목표 하루 2회 **한국시간 08:30 / 17:00**
- 수집: 공개 뉴스 RSS 검색, 선택된 공식 후보 사이트 HTML·schema.org Event, 별도 GDELT 공개 뉴스 API 및 알려진 출처 내부 대체 링크 탐색
- 저장: 전용 저장소의 `.monitor-state/state.json`에 공개 관측 이력 누적
- 배포: GitHub Pages에 **공개 조사 JSON 파일만** 발행
- 표시: 현재 RWA Radar 웹사이트가 공개 피드를 읽어 표시
- 개인 섭외 기록은 위 저장소나 공개 피드로 전송하지 않음

> **새 전용 저장소를 권장합니다.** 기존 GitHub Pages 사이트가 있는 저장소에서 이 워크플로를 실행하면 Pages 내용이 피드 사이트로 바뀔 수 있습니다. 기존 사이트를 덮어쓰지 마세요. 계정·조직에 따라 요금, 실행시간, Pages 공개·비공개 정책 및 승인 조건이 다릅니다. 무료·무제한을 보장하지 않습니다.

## 1. 설치 파일 준비

웹사이트의 **자동 조사 센터 → 연결·시작 안내 → 자동화 설치 파일 받기**를 누릅니다. 압축 파일에는 다음 파일이 포함됩니다. 첨부 원본 문서와 개인 취재기록은 포함되지 않습니다.

```text
.github/workflows/rwa-monitor.yml
automation/collector.py
automation/test_collector.py
automation/SETUP.md
automation/KEYWORDS.md
data/monitor-plan.json
README.md
.gitignore
```

ZIP을 풀어 폴더 구조를 유지하세요. `.github`는 숨김 폴더로 보일 수 있습니다. 설치 파일을 받는 것만으로 예약이 켜지지는 않습니다.

## 2. 본인 GitHub 계정에서 전용 저장소 만들기

1. GitHub에 로그인하고 새 저장소를 만듭니다. 예: `rwa-radar-research`.
2. 공개 피드를 만들 것이므로 개인 메모·연락처·비공개 기사·토큰을 넣지 마세요. 비공개 저장소에서도 Pages 이용 가능 여부는 계정 정책에 따라 달라집니다.
3. ‘Add file → Upload files’에서 압축을 푼 파일·폴더를 **원래 경로 그대로** 올립니다. ZIP 자체를 올리는 것이 아닙니다. 업로드에 `.github/workflows/rwa-monitor.yml`이 포함되었는지 꼭 확인합니다.
4. 폴더 업로드가 어려우면 개발 지원 담당자에게 이 설치 파일을 그대로 전달하세요. 코드를 새로 작성할 필요는 없습니다. 비밀번호나 액세스 토큰을 대화창에 보내지 마세요.

## 3. Pages와 Actions 설정

1. 저장소 **Settings → Pages → Build and deployment → Source**에서 `GitHub Actions`를 선택합니다.
2. **Settings → Actions → General**에서 필요한 Actions 사용이 허용되어 있는지 확인합니다. 워크플로는 공개 관측 이력을 보존하기 위한 저장소 쓰기 권한과 Pages 배포 권한을 요청합니다. 조직 정책·보호 브랜치가 이를 막으면 관리자와 정식 권한을 조율해야 합니다. 보호 정책을 우회하거나 강제 push하지 않습니다.
3. Pages 환경에 매회 승인자가 필요한 정책이 있으면 무인 예약 실행도 승인 대기할 수 있습니다. 운영·보안 정책을 소유자가 결정해야 하며 이 코드가 자동으로 보호를 해제하지 않습니다.

## 4. 처음 한 번 직접 실행

1. **Actions → RWA Radar — twice-daily research → Run workflow**를 누릅니다.
2. 검사, 공개 자료 수집, 이력 저장, 피드 배포 단계가 끝날 때까지 기다립니다. 차단·지연에 따라 수 분~수십 분이 걸릴 수 있습니다. 실패하면 로그에서 어느 단계인지 먼저 확인합니다.
3. 완료된 실행의 **Summary**에 표시되는 `Website connection URL`을 복사합니다. 실제 성공한 Pages URL을 사용하며 주소를 추측하지 않습니다.
4. 그 주소를 브라우저에서 열어 `version`, `generated_at`, `run`, `items`가 있는 JSON인지 확인합니다. HTML 로그인 화면이라면 공개 피드가 아닙니다.
5. **모든 수집 출처 실패를 포함한 실행도 진단 JSON을 발행**합니다. 배포 성공과 리서치 성공은 별개입니다. `run.status`, `run.failed`와 출처별 오류를 확인해야 합니다.

## 5. 웹사이트와 연결

1. RWA Radar의 **자동 조사 센터 → 연결·시작 안내**를 엽니다.
2. 복사한 공개 JSON URL을 붙여넣고 **연결 확인 후 저장**을 누릅니다.
3. 피드 시각, 최근 성공/실패, 실제 발견 항목을 확인합니다. 아직 발견한 기사가 없어도 출처 확인 성공 기록이 있다면 ‘결과 0건’과 ‘실행 안 됨’을 구분할 수 있습니다.
4. 연결이 차단되면 CORS, 로그인 리디렉션, 파일 주소, 계정 공개 정책을 확인하세요. 웹사이트는 다른 도메인의 인증 쿠키·API 토큰을 보내지 않습니다. CORS 차단을 무단 프록시나 공개 쓰기 API로 우회하지 않습니다.
5. 페이지가 열려 있으면 5분마다 피드를 다시 읽고, 다시 돌아오면 즉시 재확인합니다. 브라우저가 닫힌 동안의 수집은 GitHub Actions가 담당합니다.

## 6. 하루 두 번 예약 켜기

**Settings → Secrets and variables → Actions → Variables → New repository variable**에서 아래 항목을 추가합니다.

- Name: `RADAR_ENABLE_SCHEDULE`
- Value: `true`

이 값은 비밀번호가 아닌 실행 스위치입니다. 기본은 비활성입니다. `workflow_dispatch` 수동 실행은 이 스위치 없이도 소유자가 직접 요청할 수 있습니다.

예약은 기본 브랜치에 있는 워크플로에서 실행됩니다.

- UTC `30 23 * * *` → 다음 날 **08:30 KST**
- UTC `0 8 * * *` → 같은 날 **17:00 KST**

**GitHub 예약은 정각 보장 서비스가 아닙니다.** 혼잡·장애로 지연 또는 누락될 수 있고, 공개 저장소의 장기 비활성 등으로 예약이 중지될 수 있습니다. 정확히 정각에 결과가 필요하면 별도 관리형 예약 서버로 이전하고 수집 시작을 앞당겨야 합니다. GitHub 장애나 실행 자체의 미발생은 수집기가 기록할 수 없으므로 사이트에서 18시간 경과 시 갱신 지연으로 표시합니다.

다음 예약 시각 이후 실행 기록이 실제로 하나 더 생기고 웹사이트 시각도 바뀌었는지 확인해야 **가동 검증 완료**입니다. 일정 문자열이나 피드 주소 저장만으로 완료라고 판단하지 않습니다.

중지하려면 변수 값을 `false`로 바꾸거나 소유자가 워크플로를 비활성화합니다. 웹사이트의 ‘기본 피드 보기’는 표시 주소만 바꾸며 외부 예약을 중지하지 않습니다.

## 수집·검수 범위와 한계

- 두 첨부문서의 전체 본문·표·하이퍼링크를 추출해 31개 행사군, 7개 키워드 전략을 구성했습니다. 과거 행사 이력과 문서 속 2027년 날짜 주장은 독립적으로 확인된 최신 사실이 아닙니다.
- Google News RSS는 **검색 후보**입니다. 게시일을 개최일로 사용하지 않으며 기사에 나온 연사를 공식 명단으로 확정하지 않습니다. 검색 색인에 없는 공지는 놓칠 수 있습니다.
- 기본 직접 수집은 `direct: true`인 공식 후보 사이트의 홈페이지 및 관련 링크 최대 2개를 읽습니다. v2는 RSS 실패 행사군 중 회당 8개를 순환하여 알려진 URL·관련 링크·사이트 제공 RSS/Atom·사이트맵을 행사군당 최대 7회 확인합니다. 미시도·실패·2027 언급 발견을 구분하고 robots·접근 제한을 우회하지 않습니다.
- GDELT 공개 Doc API는 별도 뉴스 색인입니다. 기본 질의 2개, 질의당 최대 후보 10개·원문 확인 3개·실패 제목 재검색 1개로 제한합니다. 다른 URL에 실제 접속하고 제목 일치를 검사한 경우에만 대체 링크로 기록합니다. Google 뉴스 RSS 자체의 복구가 아니며 색인 누락·요청 실패·결과 0건을 보장할 수 없습니다.
- 웹사이트는 자동 원본을 브랜드·연도 묶음으로 대시보드·행사 목록에 함께 보여주되 개인 기록을 자동 생성하지 않습니다. 확정 행사 수와 후보 묶음 수를 구분하세요.
- 현재 수집기는 HTML 텍스트와 JSON-LD만 읽습니다. JavaScript 렌더링, 로그인 페이지, PDF, 이미지형 연사표, 영상은 자동 분석하지 않습니다. 공식 페이지가 바뀌면 파서나 직접 URL 조정이 필요합니다.
- 자동 분류·추출: 현행 구조화 Event의 날짜·아시아 개최국·감시명 일치·금융기관 및 토큰화 관련성 조건을 충족할 때만 표시합니다. **사람이 확인했다는 뜻은 아닙니다.** 정보 자체가 오래되거나 잘못되었을 가능성은 남습니다.
- 불확실·취소·연기·기간 외·지역 미확인 항목은 검수 대상으로 표시합니다. `performer` 구조화 정보가 있는 발표자만 추출하며, 인물·소속·직함을 AI로 만들어 채우지 않습니다. 대부분의 연사표는 구조화되어 있지 않아 추가 파서·수동 검수가 필요합니다.
- 현재 버전은 LLM을 사용하지 않는 규칙 기반 후보 탐색기입니다. 31개 행사군을 완전히 조사하거나 모든 스피커 변화를 감지하는 전수 모니터링을 보장하지 않습니다.

## 데이터 보존·고장 대응

- 이전 관측이 있는 상태 파일을 읽지 못하면 덮어쓰지 않고 실행을 실패시킵니다.
- 출처별 실패는 이전 발견 항목을 삭제하지 않습니다. 성공한 일부 출처만 갱신되면 `partial`로 표시합니다.
- 상태 파일은 Git에 커밋하고 강제 push하지 않습니다. 동시 편집·브랜치 정책 때문에 push에 실패하면 새 배포를 중단하며 이전 공개 피드는 유지됩니다.
- 공개 피드는 최근 변경순 최대 400건과 최근 28회 실행 기록을 표시합니다. 누적 관측은 상태 파일에 보존됩니다. 피드에서 오래된 항목이 빠지는 것은 원본 관측 삭제와 다릅니다.
- 검수 표시는 발견 ID+내용 식별자 단위로 브라우저에 저장됩니다. 새 버전이면 재검수하며 메모는 기존 JSON 백업에도 포함됩니다. 다른 기기에 자동 동기화되지 않습니다.
- 전체 실패나 페이지 fetch 실패는 ‘새 소식 없음’으로 표시하지 않습니다. 화면을 새로 연 뒤 피드가 계속 접근 불가능하면 현재 브라우저 메모와 별도로 보관한 조사결과 JSON 백업을 참고하세요.

## 확인한 것과 아직 확인하지 못한 것

- **확인:** 문서 전체 추출, 키워드 구성, 수집 규칙·실패 보존·대체 탐색·제목 재검색 등 30개 Python 단위 테스트(브라우저 Python 환경, 테스트용 네트워크 응답), 통합 UI·검수·원본 연결 등록·편집 메타데이터 보존·개인 기록 보존·업데이트 ZIP 검사, PC·모바일 시각 검증. 기존 v1 최초 운영 수집·Pages 피드 발행·브라우저 CORS 연결도 확인했습니다.
- **미확인:** 외부 GitHub의 v2 업데이트·실제 대체 링크 확보율·첫 예약 실행 성공·대시보드 자체 공개 배포. GDELT 실시험 응답은 `{}`로 후보 0건이었으며 대체 기사 확보 성공을 의미하지 않습니다. 이 단계들은 소유자 적용 후 확인해야 합니다.
